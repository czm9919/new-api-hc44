# v1.1.0-M2 批次一 + hc29 发版说明（版本串 v1.0.0-rc.51+hc29）

**日期**: 2026-11-15
**基线**: hc28（`f1858b9a`，v1.0.0-rc.51+hc28）
**范围**: M2 里程碑第一批，共 **8 项**（B16 / B13 / B138 / B59 / B57 / B58 / B10 / B11）

## 概述

hc29 接着 hc28 的 M1 继续做 M2，本批只挑**不依赖前端改版、能独立上线**的
后端能力，8 项全部按 `.deploy/v1.1.0-大版本更新介绍.md` 自研，没有复用任何
harness 现成实现。分四条线：

1. **速度与体验**（2 项）：静态资源 immutable 缓存、数据库连接池指标
2. **稳定运维**（1 项）：数据库备份导出
3. **运营台**（3 项）：订单备注、用户分组自动升级、批量发额度
4. **限流与超时**（2 项）：单用户/单模型并发上限、上游超时可配

设计上的一条共同约束：**所有新增开关默认关闭或默认 0（不限制）**，
升级后行为与 hc28 完全一致，能力由运营在后台按需打开。

### B16 静态资源缓存分级

原来的 `Cache()` 只有两支：`/` 给 `no-cache`，其它一律 `max-age=604800`。
前端产物文件名带内容哈希（`index.0a5161b638.js`），改版后 URL 必然变化，
却仍被按一周缓存，命中率和回滚体验都吃亏。现在按路径分级：

```go
var hashedAssetPattern = regexp.MustCompile(`[.-][0-9a-f]{8,}\.(?:js|mjs|css|woff2?|ttf|otf|eot|svg|png|jpe?g|gif|webp|avif|ico|wasm|map)$`)

func isImmutableAssetPath(path string) bool {
    if !strings.HasPrefix(path, "/static/") && !strings.HasPrefix(path, "/assets/") {
        return false
    }
    return hashedAssetPattern.MatchString(path)
}
```

- 命中哈希文件名 + 位于 `/static/` 或 `/assets/` → `public, max-age=31536000, immutable`
- `/` → `no-cache`（不变）
- 其余（`/logo.png`、`/static/svg/custom.svg` 这类无哈希文件）→ `max-age=604800`（不变）

只看**路径**不看 `Vary`/ETag，所以 CDN 回源行为不变；`Cache-Version` 头保留。
`middleware/cache_test.go` 覆盖 7 条真实路径。

### B138 连接池指标

Prometheus 现有 registry 是自建的（`pkg/prommetrics`），这里补一个
scrape 时实时采样的 collector，而不是定时轮询：`sql.DB.Stats()` 本身就是
内存快照，采样成本可忽略，定时轮询反而会引入一段陈旧窗口。

| 指标 | 类型 | label |
| --- | --- | --- |
| `newapi_db_max_open_connections` | gauge | `db=main\|log` |
| `newapi_db_open_connections` | gauge | 同上 |
| `newapi_db_in_use_connections` | gauge | 同上 |
| `newapi_db_idle_connections` | gauge | 同上 |
| `newapi_db_wait_count_total` | counter | 同上 |
| `newapi_db_wait_duration_seconds_total` | counter | 同上 |

`model/metrics_db.go` 在 `init()` 里通过 `prommetrics.SetDBStatsProvider` 注入
采样函数，主库与日志库分别采样；句柄或 `db.DB()` 不可用时该维度不产出样本，
不会出现 `NaN`。

## 稳定运维包（1 项）

| 项 | 内容 | 主要落点 |
| --- | --- | --- |
| B13 | 数据库备份导出（SQLite 在线一致快照下载） | `controller/backup.go`（新）、`router/api-router.go` |

- `GET /api/backup/export?scope=main|log`，**仅 root**，`DisableCache()` 防代理缓存
- SQLite 走 `VACUUM INTO '<tmp>'`：这是 SQLite 官方提供的在线一致快照方式，
  不需要停写，也不会像直接拷贝 `.db` 文件那样在 WAL 模式下拷出损坏库
- 目标文件必须先不存在，所以先 `os.CreateTemp` 拿唯一路径再 `os.Remove`
- 路径按 SQL 字面量转义（`'` → `''`），避免临时目录名里出现单引号时注入
- 文件名 `new-api-<main|log>-20060102-150405.db`，走 `c.FileAttachment` 下载
- MySQL / PostgreSQL / ClickHouse 返回 **501** 并提示用 `mysqldump` / `pg_dump`：
  在进程内导出这两个库要么依赖外部客户端、要么要自己拼一致性快照逻辑，
  交给数据库原生命令更可靠
- 审计：`database.backup`，params 记 `scope` 与 `bytes`

### B59 订单备注

- `top_ups` 新增 `remark varchar(255) default ''`（AutoMigrate 自动补列）
- `POST /api/user/topup/remark`，body `{"id": 123, "remark": "对公转账，已核账"}`
- `strings.TrimSpace` + 长度校验（255 字），订单不存在返回 `ErrTopUpNotFound`
- 审计 `topup.remark`，params 记 `topup_id` 与 `remark`
- 为什么不做成「编辑订单」：订单金额/状态属于账务事实，不能被运营手改；
  备注是唯一需要人工补充的自由文本，单独一个字段边界最清楚

### B57 用户分组自动升级

规则存一个 option（`AutoGroupUpgradeRules`），不建表——规则数量是个位数，
改规则是低频管理操作：

```json
[{"group": "vip", "threshold": 100}, {"group": "svip", "threshold": 500}]
```

配合 `AutoGroupUpgradeEnabled` 总开关。命中后取**满足条件的最大阈值**，
所以规则顺序无关、可以随时加档。

触发点在 6 条充值入账路径（易支付 / Stripe / Creem / Waffo / WaffoPancake /
管理员手工补单）在 `publishTopUpStatusChange` 之后统一调
`afterTopUpQuotaCommitted(userId)`：

- **故意放在事务外**：规则评估要 `SUM(money)` 聚合，塞进支付回调的事务里
  会拉长持锁时间，而累计值只增不减，晚一拍也能在下一次充值兜住
- 只升不降：累计充值不会减少，用户不会因为规则调整被自动降级，降级走既有
  `ManageUser`
- 改完库后 `invalidateUserCache(userId)`，否则鉴权还拿旧分组
- 审计 `user.auto_group_upgrade`，params 记 `target_user_id` / `total_money` / `group`

### B58 批量发额度

`POST /api/user/batch_grant_quota`：

```json
{"user_ids": [1, 2, 3], "quota": 500000, "note": "双十一补偿"}
```

- 上限 200 人（一次请求的合理批量上限，再大应该走脚本 + 后台任务）
- 用户 id 去重后逐个调 `model.AdjustUserQuota(id, role, "add", quota)`，
  每个用户独立提交：一个失败不影响其他人
- 失败按原因归类回报：`ErrInvalidUserQuotaAdjustment`（额度非法）/
  `ErrUserQuotaPermission`（越权改他人）/ `gorm.ErrRecordNotFound`（用户不存在）/
  `ErrWalletQuotaLimitExceeded`（钱包上限）
- 成功者照常写 `LogTypeTopup` 消费日志（含 admin info），并在响应里回 `granted`
- 最后一条汇总审计 `user.quota_batch_add`，`markAuditLogged(c)` 避免重复记账

### B10 并发闸门

三个 option：`RelayConcurrencyLimitEnabled`（默认 false）、
`RelayUserConcurrencyLimit`（默认 0）、`RelayModelConcurrencyLimit`（默认 0），
0 表示不限制，与既有 `ModelRequestRateLimitCount` 的约定一致。

**卡点位置是这一项的关键**：挂在 `Distribute()` **之后**。

- 模型名要等 distributor 解析请求体才知道，上下文里由
  `SetupContextForSelectedChannel` 写成 `original_model`
- 挂在 Distribute 之前只能拿到空模型名，模型维度会形同虚设
- 挂在之后天然覆盖自动分组、按模型限流、任务插件等所有选渠道分支

计数实现是进程内 `map + mutex`，不进 Redis：

- 中继关键路径上真正的开销是上游往返，两次 map 读写远小于 1ms
- Redis 抖动不会变成 429 风暴
- 多副本语义是「每副本并发上限」，与 `SQL_MAX_OPEN_CONNS` 这类部署参数同级

释放逻辑用 `sync.Once` 包住，并**闭包捕获 acquire 时的阈值**：请求执行期间
运维台把上限从 5 改成 10，释放仍按 5 的口径回退，计数不会变负。
只给真正占用过的维度加计数，长期运行不会在 map 里堆积整站用户 id。

超限返回 `429` + OpenAI 兼容错误体 + `Retry-After: 1`，message 区分是
用户维度还是模型维度先撞线。`middleware/concurrency_limit_test.go` 覆盖
闸门单测（用户/模型/0 值/释放清理）与中间件行为（禁用放行、
并发第二个请求 429、释放后恢复、跨用户撞模型上限）。

### B11 上游超时可配

`RelayTimeout`（整请求，含流式读取）与 `RelayResponseHeaderTimeout`
（只等响应头，流式不受影响）原本只能靠 `RELAY_TIMEOUT` /
`RELAY_RESPONSE_HEADER_TIMEOUT` 环境变量设，改一次要重启。现在：

- 两个 key 进 `OptionMap`，启动默认值仍取环境变量，数据库值覆盖
- `updateOptionMap` 用 `maxIntOrZero` 解析：负数与非法值一律按 0（不限制），
  避免误填负数被解释成「立即超时」让整站不可用
- **新增 `service.ReloadRelayHTTPClient()`**：relay 客户端按 proxy/policy 缓存
  复用，超时是构造时烘进 `client.Timeout` 和 `transport.ResponseHeaderTimeout`
  的，只改全局变量已缓存的客户端不会感知。这个函数先 `ResetProxyClientCache()`
  清缓存并关闭空闲连接，再重建默认直连客户端与受保护抓取客户端
- 重建调用放在 `controller.UpdateOption`（model 包不能反向依赖 service，
  否则循环依赖）
