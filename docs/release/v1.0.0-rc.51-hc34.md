# hc34 发版说明（版本串 v1.0.0-rc.51+hc34）

**日期**: 2026-11-17
**基线**: hc33（`v1.0.0-rc.51+hc33`，commit `c25f332b`）
**范围**: 新增「用户消耗排行榜」（管理员侧运营视图），共 **1 项功能**

## 概述

hc33 之前的运营视图都是「按渠道 / 按模型」切，缺一个「按人」的口径：
谁在这个月把额度吃掉了、头部几个人占了多少比例、消耗大的用户是不是还有
余额。本批补上这个视图，从日志库聚合出窗口内消费额度倒序的前 N 名用户。

口径上的三个决定：

1. **按 `user_id` 聚合，不按 `username`**：日志里的 `username` 是写入当时的
   快照，用户改名会把同一个人拆成两行；`user_id` 才是稳定主键
2. **展示名以 `users` 表为准**：聚合出的 `MAX(username)` 只是字典序兜底
   （跨库没有统一的时间序聚合函数），controller 用 users 表的当前用户名覆盖
   日志快照，改过名的用户看到的是现在的名字
3. **0 消耗不进榜**：`Having SUM(quota) > 0`，避免只调过免费模型 / 只失败的
   用户占榜位；但**全站汇总**仍按全部 `type=2` 日志算，两者口径在页面上分开
   标注（「总消耗」「请求数」「有消耗用户数」）

## 接口

```
GET /api/user/consumption_rank?days=30&limit=20     （管理员鉴权）
```

| 参数 | 语义 |
| --- | --- |
| `days` | 回看天数，`0` = 全部时段；缺省 30；负数按 0、超 365 按 365 |
| `limit` | 返回条数，缺省 20，上限 100（model 层同样兜底，防越权大查询） |

响应结构：

```json
{
  "success": true,
  "data": {
    "leaderboard": [
      {
        "rank": 1, "user_id": 2, "username": "bob", "display_name": "Bob Chen",
        "used_quota": 3000000, "quota_share": 0.6, "request_count": 120,
        "last_active": 1763000000, "remaining_quota": 500000,
        "lifetime_quota": 9000000, "status": 1, "deleted": false
      }
    ],
    "totals": { "used_quota": 5000000, "request_count": 218, "user_count": 3 },
    "window": { "days": 30, "start_ts": 1760418000, "end_ts": 0 },
    "generated_at": 1763000123
  }
}
```

`end_ts` 固定 0（不设上界，等于「到现在」）；`deleted: true` 表示 users 表里
已查不到该 user_id（日志库只剩历史痕迹），此时 `status` / `remaining_quota`
/ `lifetime_quota` 均为 0，页面打「用户已删除」标记。

## 升级注意

1. **无新增表、无新增 option、无数据迁移**：只读 `logs` 与 `users` 两张既有表，
   `data/` 结构与 hc33 完全一致，回滚目标是 hc33 镜像（本批未单独出镜像）
2. **日志库读放大**：`days` 越小越快；`days=0`（全部时段）在几十万行以上日志
   库上会全表聚合，已用 `limit` 上限 100 与 365 天上限兜住最坏情况
3. 新路由挂在 admin 路由组下，非管理员访问返回 403，未登录返回 401
4. 本批实际跳版上线：访问 `/api/status` 看到的是 `v1.0.0-rc.51+hc36`
   （hc34 与 hc35 合并在同一镜像里），侧边栏「用户 → 用户消耗排行榜」
   仅管理员可见
