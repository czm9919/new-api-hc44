# 发版说明：v1.0.0-rc.43+hc25 — 修复扩展设置「保存失败 / 保存不生效」

## 现象

管理员在「扩展设置」页（及号池后台）点保存后，出现两类问题：

1. **保存看起来成功了，但刷新后回到默认值 / 空白** —— 表现为「保存没生效」「保存失败」。
2. 个别保存失败时，界面只弹一句干巴巴的「保存失败」，看不到具体哪一项不合法。

## 根因

### 根因一（主）：配置读取把数组当成了 map

后端 `GET /api/option/` 返回的是**数组**形态：

```json
{ "success": true, "data": [ { "key": "CustomHeadHTML", "value": "..." }, ... ] }
```

但扩展设置里三个走 option 的卡片（自定义 Head 代码、余额显示、导航栏配置）一直按 **map** 取值：

```ts
const value = res.data?.data?.[CUSTOM_HEAD_OPTION_KEY]   // data 是数组，字符串下标永远是 undefined
```

数组用字符串下标取永远是 `undefined`，于是：

- 卡片打开时读不到已保存的值，界面永远停在默认值 / 空白；
- 实际上保存是成功的（写库成功），只是**读不回来** —— 用户保存后刷新，值又没了，自然以为是「保存失败」。

`nav-custom-card` 同理（`res.data?.data?.SidebarNavCustom` 也是 map 取值，永远 undefined）。

### 根因二（次）：号池设置保存静默吞掉业务失败

`PUT /api/key-pool/settings` 在参数不合法时，后端 `common.ApiError` 返回的是 **HTTP 200 + `success:false`**（不是 4xx）。旧前端 `updateKeyPoolSettings` 直接 `return res.data.data`，**根本没判断 `success`**，于是服务端拒绝时也走「已保存」分支 —— 假成功。错误提示里的 `(error as {response?:{data?:{message?}}})?.response?.data?.message` 在业务失败（普通 `Error`）下也永远拿不到东西。

## 修复

### 读取归一化（修根因一）

- 新增 `web/src/features/enhanced-settings/option-utils.ts`：`toOptionMap` / `optionValueOf` 把 `/api/option/` 的响应（数组形态，兼容历史 map 形态，最多剥两层 `{success,data}` 包装）归一成 `key -> value`。
- 三个卡片的读取统一改走 `optionValueOf(res.data, KEY)`，保存后刷新能正确读回已保存值。

### 业务失败不再静默（修根因二）

- 号池接口 `web/src/features/key-pool/api.ts` 全部改为 `requireServerSuccess(res.data)` 包裹：后端 `success:false` 会带上服务端文案抛出，不再被当成成功。
- 扩展设置页与号池后台的保存分支统一包 `try/catch` + `requireServerSuccess`。

### 错误文案不再空白

- 新增 `web/src/features/enhanced-settings/save-error.ts`：`describeSaveFailure(error, fallback)` 统一调用 `getServerErrorMessage`（它会把 axios error、业务报文 `message`/`message_key`、以及 `Error.cause` 都翻一遍并做 i18n），替换掉原来永远为空的 `(error as {...})?.response?.data?.message` 写法。
- 扩展设置三个卡片与号池后台、号池生成、贡献密钥等所有保存 / 操作错误提示都改用 `getServerErrorMessage` / `describeSaveFailure`，失败时给出可读的具体原因。
