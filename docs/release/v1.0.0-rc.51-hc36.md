# hc36 发版说明（版本串 v1.0.0-rc.51+hc36）

**日期**: 2026-11-17
**基线**: hc35（`v1.0.0-rc.51+hc35`）
**范围**: 1 个越权修复 + 1 个 PAT scope 存量缺陷补齐 + 新增「安全巡检」管理页

## 概述

hc36 是一个**安全向**批次，三件事：

1. **修一个真实可利用的越权**：`GET /api/token/risk/overview`（hc31·B93
   的密钥泄露风险检测）原本挂在 `tokenRoute`（仅 `UserAuth()`），意味着
   **任何已登录用户**都能拉到全站跨用户的密钥风险证据——别的用户被标记
   为 high 风险的密钥名、用户名、来源 IP 清单、用量、处置建议。这个接口
   的定位是管理员巡检（修复用 `git stash` 回退后实测验证：普通用户 200，
   响应体里能看到 `username:"risk-plain-user"`、5 个 IP 和推荐处置文案）。
   修复后移入独立 `AdminAuth()` 子组。
2. **补齐 hc34 遗留的 PAT scope 登记**：`GET /api/user/consumption_rank`
   （消费排行，hc34 引入，挂 `AdminAuth`）漏登在
   `middleware/access_token_routes.go`，导致 Personal Access Token 访问它
   恒为 403 `ACCESS_TOKEN_ROUTE_UNDECLARED`；全量护栏测试
   `TestAccessTokenRouteRulesCoverEveryDashboardRoute` 因此在 HEAD 上就红
   （同样用 `git stash` 证明是存量而非本次回归）。按「用户管理读」补
   `user:read` scope。
3. **新增管理员「安全巡检」页**（`/security-overview`）：把跨用户密钥
   风险汇总 + 全站两步验证覆盖率放进一个页面，运营不用再在用户侧自查页
   和设置统计之间来回拼信息。

## 越权修复详情

```
修复前: tokenRoute (UserAuth)      → GET /api/token/risk/overview   任意登录用户可读
修复后: tokenAdminRoute (AdminAuth) → GET /api/token/risk/overview   仅管理员
```

- 影响面：`user_id` / `username` / `token_name` / 来源 IP 列表 / 请求量 /
  `recommendation`（处置建议）跨用户泄露
- 新增回归护栏 `router/token_risk_router_test.go`（2 个用例）：
  1. `TestTokenRiskOverviewRouteRequiresAdmin`——表驱动：匿名 401 /
     普通用户 403 / 管理员 200（打真实 `SetApiRouter` + `CreateLoginSession`
     签发的 JWT）
  2. `TestTokenRiskOverviewAdminSeesCrossUserEvidence`——管理员查询能看到
     **其他用户**的高风险密钥证据（`distinct_ips >= 5`），证明修复没有把
     接口功能废掉，只收紧了鉴权

## PAT scope 补齐

`middleware/access_token_routes.go` 新增 1 行：

```go
"GET /api/user/consumption_rank": accessTokenScopeRule("user:read"),
```

护栏测试 `TestAccessTokenRouteRulesCoverEveryDashboardRoute` 恢复全绿。

## 页面设计口径

1. **只展示 `risk_level !== ''` 的密钥**：管理端巡检关心「有问题的那几把」，
   不是全量清单；排序按风险等级（high → medium → low）+ 请求数降序
2. **窗口切换走后端**（`days` 参数），搜索与 CSV 走本地结果集——与
   hc35 渠道健康页一致
3. **2FA 覆盖率来自 `GET /api/user/2fa/stats`**：`enabled_rate` 直显 +
   `{{enabled}} / {{total}} 位用户` hint；两张卡片同屏，口径不变
4. **类型单点定义**：`security-overview/api.ts` 直接 re-export
   `token-risk/api` 的 `TokenRiskReport/TokenRiskItem/TokenRiskIP`，用户侧
   自查页与管理端巡检共用同一份后端契约

## 接口


`TokenRiskReport` 结构与 hc31 完全一致，无契约变更；这里不再复述字段。

### 线上越权实测（跳版部署后的真实请求）

| 身份 | 请求 | 结果 |
| --- | --- | --- |
| 匿名 | `GET /api/token/risk/overview` | **401** `AUTH_UNAUTHORIZED` |
| 普通用户（JWT） | `GET /api/user/self` | 200 `role:1`（证明登录链路有效） |
| 普通用户（JWT） | `GET /api/token/risk/overview` | **403** `AUTH_INSUFFICIENT_PRIVILEGE` |
| 管理员（JWT） | `GET /api/token/risk/overview?days=30&limit=100` | **200** `{window_days:30,total_tokens:0,risky_tokens:0,items:[]}` |
| 管理员（JWT） | `GET /api/user/consumption_rank?days=30&limit=5` | **200**（hc34 功能 + scope 修复同时验证） |
| 管理员（JWT） | `GET /api/channel/health/overview` | **200**（hc35 功能同步验证） |
| 管理员（JWT） | `GET /api/user/2fa/stats` | **200** `{total_users:2,enabled_users:0,enabled_rate:"0.0%"}` |

实测要点：同一枚普通用户 JWT 在 `/api/user/self` 上是 200、在风险巡检上是 403，
说明拒绝来自**权限判定**而不是未登录——正是本次修复要的行为。测试账号与
会话已在验证后清理，站点用户表恢复为初始 1 个 root。

> 踩坑记录：直接改 sqlite 给测试账号提权后必须**停容器再启动**，否则容器
> 的 SQLite 连接会在重启时把旧 WAL checkpoint 回来、覆盖外部写入（表现为
> 库里 role=10 但接口仍 403）。


## 升级注意

1. **无新增表、无新增 option、无数据迁移**：风险数据仍是 hc31 的只读
   日志聚合，`data/` 结构与 hc35 完全一致。注意本批是**跳版上线**：
   hc34/hc35 的镜像从未构建过（当时 Docker Desktop 起不来），线上是
   hc33 直接升到 hc36，所以回滚的实际目标镜像是 hc33
2. **行为变化只有一处**：`/api/token/risk/overview` 从「任何登录用户可调」
   收紧为「仅管理员」。若有第三方脚本以普通用户身份轮询该接口，升级后会
   开始收到 403——这是预期收紧，不是故障
3. **PAT 消费排行恢复可用**：hc34 起 PAT 访问 `/api/user/consumption_rank`
   恒 403 `ACCESS_TOKEN_ROUTE_UNDECLARED`，本版补齐后持有 `user:read`
   scope 的 PAT 可正常调用
4. 升级后访问 `/api/status` 确认 `version` 为 `v1.0.0-rc.51+hc36`，并以
   普通用户 + 管理员两个身份各调一次 `/api/token/risk/overview`，确认
   403 / 200 两种结果
