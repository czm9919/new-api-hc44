# v1.1.0-M2 批次二 + hc30 发版说明（版本串 v1.0.0-rc.51+hc30）

**日期**: 2026-11-16
**基线**: hc29（`v1.0.0-rc.51+hc29`）
**范围**: M2 里程碑第二批，共 **11 项**（B95 / B96 / B100 / B99 / B60 / B105 / B114 / B64 / B63 / B222 / B223）

## 概述

hc30 接着 hc29 继续 M2，本批聚焦**买家侧 + 计费侧**两条线，11 项全部按
`.deploy/v1.1.0-大版本更新介绍.md` 自研，没有复用任何 harness 现成实现：

1. **计费护栏**（3 项）：按次扣费上限、最低余额门槛、税率展示口径
2. **买家侧**（2 项）：发票抬头簿、邀请排行榜
3. **账单透明**（2 项）：扣费明细下钻、请求耗时分布
4. **主动运营**（2 项）：用量异常提醒、模型公告位
5. **导入迁移**（2 项）：用户批量导入、第三方价格表导入（LiteLLM / OpenRouter）

与 hc29 相同的设计约束：**所有新增开关默认关闭或 0（不限制）**，升级后行为
与 hc29 完全一致，能力由运营在后台按需打开。

| 项 | 内容 | 主要落点 |

### B95 / B96 扣费护栏

两个新配置项挂在既有 `quota_setting` 嵌套配置上：

```json
{
  "quota_setting.per_call_quota_cap": 0,
  "quota_setting.min_wallet_quota_usd": 0
}
```

- `per_call_quota_cap`：按次计费单次扣费上限（quota 单位）。`ClampPerCallQuota`
  在扣费处夹紧，0 / 负值均表示不限制（读取时负数归零，避免把「0 上限」
  误判成「全部免费」）
- `min_wallet_quota_usd`：以 USD 表达的最低余额门槛，内部换算 quota 单位。
  **允许负值**用于欠费宽限：设 -2 表示余额跌到 -2 USD 才拒绝新请求；
  拒绝时返回 i18n 文案 `quota.below_min_wallet`（`Remaining` / `Min` 占位符）
- 两者都接入 `model/option.go::validateOptionValue` 校验链：非法值在保存
  入口就报错，不会存进数据库

### B100 税率展示

`tax_setting` 嵌套配置（`enabled` / `rate_percent` / `display_mode` /
`label` / `invoice_note`）：

- **只影响展示口径与账单标注，不参与实际扣费**：扣费仍按倍率/按次价格原样计算
- `display_mode`：`include`（价目已含税） / `exclude`（价目未含税，需另加）
- `GrossFromNet` / `NetFromGross` 双向换算（6% 未税 100 ↔ 含税 106 往返一致）
- 公开价目接口通过 `PublicInfo()` 只暴露前台需要的 5 个字段，不给运营内部字段
- 校验：`rate_percent` 必须在 [0, 100]，启用时必须 > 0，display_mode 枚举。
  **实现上有一个关键点**：`config.UpdateConfigFromMap` 对无法解析的浮点值会
  静默跳过，借它做校验时 `"abc"` 这类脏值会一路存进数据库却看起来「校验通过」，
  所以 `ValidateTaxOption` 对 `tax_setting.rate_percent` 直接 `strconv.ParseFloat`

### B99 发票抬头簿

字段：`name` / `type`（personal | company）/ `tax_id` / `address` / `phone` /
`bank_name` / `bank_account` / `is_default`。约束：

- 企业抬头必须填纳税人识别号；个人抬头不需要
- 默认抬头**互斥**：插入或更新为默认时先取消该用户原有默认
- 删除默认抬头时补位：只在「已无默认抬头」时把最近一份设为默认，
  避免删非默认抬头时误设造成双默认

### B63 邀请排行榜

`GET /api/user/aff/leaderboard?limit=10`：

- 榜单默认 10 条、上限 50 条，门槛 `aff_count >= 1`（0 人的不上榜，
  也保护低活跃用户隐私）
- 用户名脱敏按 rune 处理（中文/emoji 安全）：保留前 2 字符 + `****` + 末 1 字符，
  ≤3 字符的短名只保留首字符
- 响应同时带 `self`：本人 `rank`（并列同名次，未上榜为 0）、`total`、`aff_count`

## 账单透明包（2 项）

| 项 | 内容 | 主要落点 |
| --- | --- | --- |
| B60 | 扣费明细下钻（单价 × token × 倍率 逐项拆解） | `controller/log_detail.go`（新）、`model/log_single.go`（新） |
| B114 | 请求耗时分布（p50/p75/p90/p95/p99） | `controller/log_detail.go`、`model/log_latency.go`（新） |

### B60 扣费明细下钻

`GET /api/log/self/detail/:id`（也支持 `GET /api/log/self/detail?request_id=`，
ClickHouse 日志库 id 非稳定自增时用 request_id 定位更可靠）。

`buildLogBillingBreakdown` 从日志 `other` 公共元数据（与
`service/log_info_generate.go::SetPublic` 写入键一一对应）拆出：

- **按量计费**（per_token）：
  `recomputed = (billable_prompt × model_ratio + completion × completion_ratio × model_ratio + cache × cache_ratio × model_ratio) × group_ratio`
  其中 `cache_tokens = min(other.cache_tokens, prompt_tokens)`，计费输入按
  `prompt - cache` 计
  - 同时给出 `unit_price_usd_per_million`（input / output / cache 三个
    USD/百万 token 单价，换算口径 `ratio / QuotaPerUnit × 1e6`）
- **按次计费**（per_call）：`单次价(USD) × 额度单位 × 分组倍率`
- 返回 `recomputed_quota` 与日志实扣的 `difference`：重算只用于展示解释，
  不改变任何计费结果
- 用户视角只能查自己的日志，`other` 里的 admin/root 信息不透出

### B114 请求耗时分布

`GET /api/log/self/latency?start_timestamp=&end_timestamp=&limit=`：

- 默认最近 7 天，样本上限 10000 条（拉取时按时间倒序 + Limit，不为算分位数
  把整张大表拉进内存），只统计成功计费且 `use_time > 0` 的请求
  （0 表示上游没回耗时，剔除避免 p50 被拉到 0）
- 百分位用最近邻秩法（`ceil(p/100×n)`，下标夹紧），另有 count / avg / min / max
- 附带 `total_requests`（时间窗内全部计费请求含 use_time=0），便于前端提示
  样本覆盖率

## 主动运营包（2 项）

| 项 | 内容 | 主要落点 |
| --- | --- | --- |
| B105 | 用量异常提醒（当日消耗远超日均时通知用户） | `setting/operation_setting/usage_alert_setting.go`（新）、`service/usage_alert_task.go`（新）、`model/log_usage.go`（新） |
| B64 | 模型公告位（下架/停服/维护通知） | `model/model_notice.go`（新）、`controller/model_notice.go`（新） |

### B105 用量异常提醒

- 配置：`usage_alert_setting.enabled`（默认 false）/ `multiplier`（默认 3，
  必须 > 1）/ `baseline_days`（默认 7，1-90）/ `min_daily_quota`（默认 0）/
  `notify_admins`（默认 false）
- 判定是**纯函数** `EvaluateUsageAnomaly`：当日消耗 ≥ 近 N 天日均（只统计
  有消耗的天，至少 2 个样本）× 倍率，且当日消耗 ≥ `min_daily_quota`
  （避免小额消耗被噪声放大误报）时触发
- 聚合用 `SumQuotaByUserInWindow`：只统计 `LogTypeConsume`，按 user_id 分组，
  方言安全（无日期函数）
- 定时任务每小时 tick，按北京时区对齐日界；`sync.Once` + `common.IsMasterNode`
  + `gopool.Go`，`atomic.Bool` 防重入；多节点只有主节点跑
- 已提醒去重表按天累积（key `yyyy-mm-dd|userId`），**每轮跨日清理旧 key**，
  避免长期运行内存无界增长
- 通知走既有 `NotifyUser` + `dto.NotifyTypeUsageAnomaly`，按用户语言渲染
  （`notify.usage_alert_title/content`，占位符 `Today/Baseline/Ratio`）；
  `notify_admins` 开启时同时 `NotifyChannelWatchers`
- 用户级开关复用 `userSetting.QuotaWarningEnabled`

### B64 模型公告位

- 字段：`model_name`（空 = 全站公告，支持 `openai/*` 通配前缀）/ `level`
  （info | warning | deprecation）/ `title` / `content` / `start_time` /
  `end_time` / `enabled`
- 公开接口 `GET /api/model_notice/active?model_name=xx`：匿名可读，只返回
  当前生效（启用 + 已开始 + 未结束）的公告；非空 model_name 时返回
  全站公告 + 该模型（含通配）的公告
- 后台 CRUD 挂 admin：`GET|POST /api/model_notice/`、`PUT|DELETE /api/model_notice/:id`
- 修复了一个真实缺陷：`Enabled` 带 `default:true` 标签时 GORM `Create` 会
  省略零值字段，「新建即禁用」永远写成 true —— `InsertModelNotice` 建后按
  意图回写 `enabled`

| 项 | 内容 | 主要落点 |

### B222 用户批量导入

`POST /api/user/batch_import`（admin + `user:write`）：

```json
{
  "users": [{"username": "u1", "password": "...", "email": "...",
             "group": "default", "quota_usd": 5}],
  "dry_run": false
}
```

- 上限 500 人/次；`dry_run=true` 只校验不写库，返回逐行结果
- 每一行独立事务，单行失败不影响其他行；响应逐行回 `ok / message / user_id`，
  顶层汇总 `total / created / failed / dry_run`
- 校验口径与「创建用户」一致：用户名/密码必填、结构 tag 校验、角色不得
  高于操作者、分组必须已配置
- `quota_usd` 为初始赠送额度（USD 填写更直观），按 `Insert` + `IncreaseUserQuota`
  两步补账，避免 GORM 零值问题
- 批内 username 重复会被识别为失败行

### B223 价格表导入

`POST /api/option/import_model_configs`（admin + `option:write`）：

```json
{"format": "auto", "data": {...}, "dry_run": true}
```

- `format`：`litellm` / `openrouter` / `auto`（按顶层结构特征自动识别）
- **换算口径**：new-api 的 `ratio` 满足「百万 token 美元单价 = ratio /
  QuotaPerUnit × 1e6」，因此 `ratio = 单 token 美元价 × QuotaPerUnit`；
  `completion_ratio = output / input`，下限 1
- 只导入价格口径清晰（`input_cost_per_token` / `output_cost_per_token`）的
  条目；LiteLLM 的 `input_cost_per_second` 等其他计价方式不支持，跳过并
  在响应里列出跳过原因
- 上限 2000 个模型；逐行返回新旧倍率对照（含 USD/百万 token 单价）与
  `conflict` 标记（已有倍率与新值不同），`conflicts` 顶层汇总
- `dry_run=true` 只预览不落库；确认后 `dry_run=false` 真正落库——落库是
  **合并写回**（以现有 ModelRatio/CompletionRatio 为底，导入条目覆盖同名
  模型），不会清掉未涉及的模型配置
