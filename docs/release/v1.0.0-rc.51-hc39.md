# hc39 发版说明（版本串 v1.0.0-rc.51+hc39）

## 概述

hc38 交付了机器人接入的管理端设置（令牌生成/轮换/撤销、字段级校验），但
`/api/qq/agent/*` 这三个接口本身**一个限流都没有**：`POST /verify` 只挂了 body
size 上限，`GET /verify` 和 `GET /ping` 完全裸奔。这意味着一枚泄露的服务令牌可以
无限次调用绑定接口，每次都要查一次 `qq_bind_codes`、失败再写一次 `users`——把一次
凭据泄露放大成打库放大器；而 `GlobalApiRateLimit` 是按全站 API 共享的桶，真出事时
它同时也在拦正常用户，不能当专用防线。

hc39 只做一件事：给这三个接口挂上**按机器人出口 IP 的固定窗口限流**。

### 为什么口径和别的限流不一样

站内其它限流都按「一个人」算，这里按「一个群」算：

- 调用方是 AstrBot 机器人，不是浏览器。机器人部署在一台机器上，**出口 IP 固定**，
  整群成员的绑定请求都从同一个 IP 进来。
- 若照搬 `rateLimitFactory(60, 60)` 那种单用户口径，一个几百人的活跃群会在同一分钟
  里互相挤占预算；而攻击者换 IP 就完全绕过，防护方向搞反了。

所以默认预算按群规模给：**120 次/分钟**。绑定码 TTL 是 10 分钟
（`model/qq_bind.go:26`），120/min 折合一个窗口内 1200 次绑定——足够几百人的群
在一次公告后集中绑定；同时把「令牌泄露后无限刷」压成一个有上界的速率。

## 变更

```go
// common/constants.go
QQAgentRateLimitEnable   bool
QQAgentRateLimitNum      int   = 120
QQAgentRateLimitDuration int64 = 60
```

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `QQ_AGENT_RATE_LIMIT_ENABLE` | `true` | 关掉即完全不加限流（不推荐，仅排障用） |
| `QQ_AGENT_RATE_LIMIT` | `120` | 每窗口允许的请求数（按出口 IP 计） |
| `QQ_AGENT_RATE_LIMIT_DURATION` | `60` | 窗口秒数 |

| 位置 | 变更 |
| --- | --- |
| `common/constants.go` | 新增三个变量 + 口径注释 |
| `common/init.go` | `InitEnv` 读三个 env（与 `GLOBAL_API_RATE_LIMIT*` 同风格） |

### 复用的既有能力（没有新写限流器）

- **固定窗口 + Lua 原子计数**（Redis 路径）：`redisFixedWindowScript`
- **Redis 故障降级内存窗口**：`fallbackMemoryIPRateLimiter`（hc 系列 B12 已做），
  限流是可用性组件，不把 Redis 抖动放大成 500
- **429 + `Retry-After`**：`writeRateLimited`。注意 429 **无 JSON body**——这是既有
  行为，插件侧 v1.0.1 已把 429 单独映射成人话（"请求过于频繁，请稍后重试"），不会
  落到「绑定失败（HTTP 429）」这种干巴巴的报错

### 一个已知的口径边界

`c.ClientIP()` 的取值依赖 Gin 的 `TrustedProxies` 配置：

- 站点在反向代理后、代理**未受信** → 所有请求落到同一个 key，等价全局限流；
- 代理**受信**但 `X-Forwarded-For` 未清洗 → 限流可被伪造头绕过。

这与站内其它所有 IP 限流同一口径，不是本次引入的问题，已在中间件注释里写明，部署侧
按需配置 `SetTrustedProxies` 即可。

三个子用例分别锁：

1. **Redis 路径**：阈值 3 时第 4 次 429、`Retry-After: 47`、计数器键为
   `rateLimit:v2:ip:QA:<ip>` 且 TTL = 窗口；另一个出口 IP 有独立预算（不互相牵连）
2. **内存路径**（`RedisEnabled=false`）：同样 3 次后 429，`Retry-After` 用整窗口作
   保守上界
3. **开关关闭**：`QQAgentRateLimitEnable=false` 时连发 6 次全部放行

### 线上

`verify-hc39.py`（workspace 根，170 行，15 条断言）已就绪，但**尚未跑过真站点**——
Docker 起不来（见下节）。脚本全程用**故意错误的令牌**，一次绑定都不会发生，也不写库：

| 阶段 | 断言 |
| --- | --- |
| 0 | `/api/status` 200，版本串 `v1.0.0-rc.51+hc39` |
| 基线 | 错误令牌 → 401（`QQ_AGENT_UNAUTHORIZED`）或 503（`QQ_AGENT_UNAVAILABLE`） |
| A | 连发 `N+1` 次：前 `N` 次业务拒绝、第 `N+1` 次 429，带 `Retry-After ∈ (0, 60]`，中途无意外状态码 |
| B | 冷却期内再发 3 次仍全 429 |
| C | 等 `Retry-After` 秒后回到业务拒绝（证明是窗口过期不是永久拉黑） |
| D | 先打 `N` 次 `/ping` 吃掉整桶，紧接着 1 次 `/verify` → 429（证明共享同桶） |
| 收尾 | 再等一个窗口，回到业务拒绝；`/api/status` 仍 200 |

```bash
python verify-hc39.py            # 默认 BUDGET=120
python verify-hc39.py 300        # 线上改过 QQ_AGENT_RATE_LIMIT
```

脚本已对着不可达端口空跑过一遍：15 条断言干净地 FAIL（不是抛栈崩溃），说明
网络异常被 `(URLError, OSError, HTTPException)` 兜住，站点半死不活时也不会中断。
**耗时约两个窗口（默认 120 秒）**，建议低峰跑。

## 升级注意

1. **纯新增中间件**，无接口签名/响应体变化；hc38 的插件不用改
2. 若群规模很大（一次公告上千人同时绑定），把 `QQ_AGENT_RATE_LIMIT` 调到
   `600` 或更高；反之若只服务一个小群，调到 `60` 收紧更安全
3. `/ping` 与 `/verify` **共享同一个桶**（都挂在 group 上）。监控如果每 5 秒 ping
   一次，会占掉 12/min 的预算，排预算时算进去
4. 429 是**临时性**响应，插件侧重试即可；不是「令牌错」也不是「码失效」
5. 回滚：换回 hc38 镜像，限流中间件随之消失（无数据/表结构变更）

## 附：pi-provider-newapi 兼容性（静态核对）

站点起不来，`verify-pi-compat.py` 跑不了，但**契约可以静态对齐**：读了
`ttimasdf/pi-provider-newapi` 的 `src/discovery.ts`、`src/models.ts`、`src/constants.ts`，
和我们这边的响应构造逐条比。

| 客户端要求 | 我们的实现 | 结论 |
| --- | --- | --- |
| `GET /api/ratio_config` 的 `data` 是 `model_ratio` 等**扁平数字 map** | `controller/ratio_config.go:19` → `ratio_setting.GetExposedData()`（`setting/ratio_setting/exposed_cache.go:44`）给 `model_ratio` / `completion_ratio` / `cache_ratio` / `create_cache_ratio` / `model_price` 五个 `map[string]float64` | 兼容 |
| `data` 里出现嵌套对象时要能容忍 | `billing_setting.GetPricingSyncData`（`setting/billing_setting/tiered_billing.go:189`）会额外合并 `billing_mode` / `billing_expr` 两个嵌套 map | **兼容**：客户端是按 key 取四个 ratio map（`models.ts: parseRatioConfig`），**从不遍历 data 顶层**，多余字段零影响 |
| 要读 `model_price` | 我们给了 | 客户端不读（`Ratios` 只有四个字段），无影响 |
| `GET /v1/models` 必须 200 + `data[]` | `router/relay-router.go:21` 挂 `TokenAuth`，带 key 即 200 | 兼容（**必须带 key**，否则 401，客户端按 auth 错处理；这是 `TokenAuth` 的既有行为） |
| 条目要有 `id` / `owned_by` / `supported_endpoint_types` | `relaykit/dto/pricing.go:6-12` 全给，且 `constant.EndpointType` 是 `types.EndpointType` 别名 | 兼容 |
| 空 `data[]` 视为刷新失败、保留旧缓存 | 无可用模型时才为空 | 无冲突 |
| `supported_endpoint_types` 能映射到 Pi 的 API | 我们发 `openai` / `openai-response` / `anthropic` / `gemini` / `embeddings` / `image-generation` / `jina-rerank` / `openai-video`；客户端 `ENDPOINT_TYPE_TO_APIS` **只认 `openai` 和 `anthropic` 两个 key** | **部分**，见下 |

### 唯一的 gap（可诊断，不是协议不一致）

`models.ts: pickModelApi(preferred, gatewayApis)` 在 `gatewayApis` 为空时落到
`DEFAULT_MODEL_API = "anthropic-messages"`。于是：

- **只**声明 `gemini` / `embeddings` / `image-generation` 的模型 → 被当成 `anthropic-messages` 调用
  → 打到 `/v1/messages` → 该模型没有 anthropic 端点 → 报错
- **只**声明 `openai-response`（我们用的是单数）的模型同理 —— 客户端认的 key 是 `openai`

主站以 `openai` / `anthropic` 模型为主时**开箱可用**；有 gemini-only 或 responses-only
模型时，用客户端的 `provider-newapi.json → modelApiOverrides`（正则 → api）补一条即可。

不改我们这侧：往 `supported_endpoint_types` 里塞 `openai` 来「冒充」`openai-response`，
会让其它按 OpenAI 兼容协议读这个字段的客户端把模型打到错误端点——比让对方加一行
override 危险得多。
