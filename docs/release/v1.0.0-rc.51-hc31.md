# v1.1.0-M2 批次三 + hc31 发版说明（版本串 v1.0.0-rc.51+hc31）

**日期**: 2026-11-16
**基线**: hc30（`v1.0.0-rc.51+hc30`，commit `ee69ba2a`）
**范围**: M2 里程碑第三批，共 **7 项**（B89 / B90 / B93 / B211 / B213 / B12 + 前端三页）

## 概述

hc31 接 hc30 继续 M2，本批四类能力全部自研（未复用任何 harness 现成实现）：

1. **计费收紧**（1 项）：免费额度可用**模型**白名单，与既有分组白名单「同时满足」才放行
2. **用户洞察**（2 项）：成本优化建议（B90）、密钥泄露风险自查（B93）
3. **通知闭环**（2 项）：站内收件箱（B211）、通知事件覆盖表（B213）
4. **稳定运维**（1 项）：Redis 故障显式降级 + 健康端点（B12）

外加三张前端页面（成本优化建议 / 密钥风险自查 / 通知中心）与侧边栏入口、
中英词条。与 hc29/hc30 相同的设计约束：**新增开关默认「不限制」**，
升级后计费行为与 hc30 完全一致，能力由运营按需打开。

## 计费收紧包（B89）

| 项 | 内容 | 主要落点 |
| --- | --- | --- |
| B89 | 免费额度可用模型白名单（逗号分隔 + `prefix*` 通配） | `model/user.go`、`service/quota.go`、`service/billing_session.go` |

- 新 option `FreeQuotaAllowedModels`，与 `FreeQuotaAllowedGroups` 同一套语义：
  逗号分隔、逐项去空白、空串 = 不限制
- 判定收敛到一个函数 `model.FreeQuotaUsable(group, modelName)`：
  **分组白名单与模型白名单必须同时放行**，任一为空表示该维度不限制
- 计费身份用 `relayInfo.GetBillingModelName()`（缺省回落 `OriginModelName`），
  保证虚拟定价别名下的判定与实际扣费一致
- 三处调用点统一改为 `relayFreeQuotaUsable(relayInfo)`：预扣可用余额计算
  （`billing_session.go`）、补扣扣减路径（`quota.go::postConsumeQuotaWithResult`）、
  消费明细资金来源标注（`quota.go::appendFundingSource`），避免预扣吃免费、
  补扣吃付费的不一致
- 白名单外的模型只扣**付费余额**（`DecreaseUserQuotaPaidOnly`），免费额度原样保留
- 管理端两个入口都能改：号池设置面板（`features/key-pool`）与 Enhanced Settings
  的隔离卡片（`features/enhanced-settings`）

## 用户洞察包（B90 / B93）

| 项 | 接口 | 权限 |
| --- | --- | --- |
| B90 | `GET /api/user/cost-insight?days=` | `usage:read` |
| B93 | `GET /api/user/token-risk?days=` | `api_key:read` |
| B93（管理端） | `GET /api/token/risk/overview?days=` | 管理员 |

### B90 成本优化建议

- 数据源：`model.GetUserModelUsageSince(userId, since)` 按 `model_name` 聚合
  近 N 天 `type=consume` 的 `quota` / `prompt_tokens` / `completion_tokens` / 请求数
- 窗口校正 `NormalizeCostInsightDays`：缺省 30 天、上限 90 天（防全表扫描）
- 逐模型给出 `model_ratio`（`ratio_setting.GetModelRatio`）、`completion_ratio`、
  `effective_ratio`（按输入/输出 token 构成折算的综合倍率）与 `quota_share`
- 建议生成规则：仅对 `quota_share >= 10%` 的模型出建议，最多 3 条、
  每条最多 3 个替代；`quota_share >= 50%` 标为 `dominant_model`，否则
  `cheaper_alternative`
- 替代模型只从该用户**可用模型集合**里选（不会推荐用不了的低价模型），
  节省额度按「token 构成不变、仅按倍率差折算」估算，属保守近似
- `quota_share` / `estimated_saving_percent` 均为 **0~1 小数**，前端展示时 ×100

### B93 密钥泄露风险自查

- 数据源：`model.GetTokenIPUsageSince(since)` 按 `token_id + ip` 聚合近 N 天消费日志
- 两条风险规则：
  - `ip_outside_allowlist`：实际请求 IP 不在该 token 的 `allow_ips` 白名单内
  - `multi_ip`：不同 IP 数 ≥ 3（`TokenRiskHighIPThreshold` 5 个直接判高风险）
- 风险等级取值 `high` / `medium` / `low` / 空串（无风险），随条目返回
  `reasons[]`、`distinct_ips`、逐 IP 明细（`allowed` 标记）、
  `last_used_at` 与 `recommendation` 处置建议
- 用户侧只看自己的 token；管理端概览跨用户聚合（`GetTokensByIds` 批量补
  token 名称，避免 N+1）

## 通知闭环包（B211 / B213）

### B211 站内收件箱

- 新表 `notifications`（`model/notification.go`，AutoMigrate 自动建表）：
  `user_id` / `type` / `title` / `content` / `is_read` / `created_at` / `read_at`
- 落库位置在 `service.NotifyUser`（**所有用户通知的唯一出口**）内部，
  因此「没配任何外部渠道」「邮件/webhook/bark 发送失败」都不会丢通知
- 正文用 `RenderNotifyContent` 按 `{{value}}` 逐项替换，与各渠道发送口径一致
- 单用户上限 200 条（`NotificationMaxPerUser`），超限按 `created_at desc, id desc`
  裁剪最旧记录，避免无界增长
- 四个接口：

| 接口 | 说明 |
| --- | --- |
| `GET /api/user/notifications?page=&page_size=` | 分页列表 + `unread_count`；`page_size` 缺省 20、上限 100 |
| `GET /api/user/notifications/unread-count` | 未读角标轮询 |
| `POST /api/user/notifications/read-all` | 返回 `{marked}` |
| `POST /api/user/notifications/:id/read` | 已是已读或记录不存在时返回 `success:false` |

### B213 通知事件覆盖表

- `GET /api/option/notify_event_catalog`（`option:read`）：把散落在各处的通知
  触发点收敛成一份静态目录——事件 × 渠道 × 默认开关 × 用户偏好字段
- 每条含 `event` / `name` / `notify_type` / `audience`（user / admin）/
  `preference_key` / `preference_type` / `default_enabled` / `channels[]`
- 偏好类型三态：`tri_state_bool`（nil = 按默认策略）、`bool_default_off`、
  `channel_type`（email / webhook / bark / gotify 单选）
- 站内收件箱渠道在目录里恒为 `default_enabled: true`，运营可据此判断
  「这条事件关掉邮件后还剩哪些渠道」

## 稳定运维包（B12）

| 项 | 内容 | 主要落点 |
| --- | --- | --- |
| B12 | Redis 限流故障显式降级 + 健康端点 | `common/redis_health.go`、`middleware/rate-limit.go`、`middleware/model-rate-limit.go` |

- **修改前**：Redis 抖动时限流中间件直接返回 **500**，等于把外部依赖故障
  放大成全站不可用
- **修改后**：限流检查出错 → 记 `common.MarkRedisFailure(op, err)` → 降级到
  内存限流器（`fallbackMemoryIPRateLimiter` / `memoryRateLimitHandler`），
  key 口径与 Redis 版一致（同 mark + 同 subject/窗口），降级期间**限流语义
  不放松**；Redis 恢复后按成功调用清零失败计数
- 连续失败 3 次（`redisDegradeFailureThreshold`）进入 `degraded`，只打一次告警；
  状态转移日志有 1 分钟冷却期（`redisHealthLogCooldown`），防故障期日志风暴
- 新端点 `GET /api/health/redis`（**root 专属**，`DisableCache`）：返回
  是否降级、连续失败数、累计降级次数、最近错误与最近成功/失败时间，
  半夜排障不用翻日志

## 升级注意

1. 重启后 `notifications` 表由 `migrateDB` AutoMigrate 自动创建，无需手工 SQL
2. `FreeQuotaAllowedModels` 默认为空 = 不限制，升级后计费行为与 hc30 一致；
   只填模型不填分组时，**分组维度仍按 `FreeQuotaAllowedGroups` 判定**
3. Redis 降级日志会以 `falling back to memory limiter` 关键字出现，
   排查限流是否降级看 `GET /api/health/redis`（root）
4. 成本优化建议 / 密钥风险自查均为**读日志库聚合查询**（`type=consume`
   有索引），大站点建议按需触发、不要高频轮询；两接口窗口上限均为 90 天
5. 通知中心单用户上限 200 条，超限自动裁剪最旧记录；外部渠道配置不影响
   站内收件箱
6. 升级后访问 `/api/status` 确认 `version` 为 `v1.0.0-rc.51+hc31`
