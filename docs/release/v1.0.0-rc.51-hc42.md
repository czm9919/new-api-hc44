# v1.0.0-rc.51 · hc42：官方定价自动同步（定时 + 按需）

hc41 把「官方价」变成了排行榜的一列，但那一列要靠管理员手点。这一版把它
接上网络：**后端定时自己去拉，快照过期时用户访问排行榜还会顺手补一次**。
管理员不再需要记得点按钮，用户也不会看到上周的价格。

## 1. 三层刷新，各管一段

| 层 | 触发 | 间隔 | 作用 |
| --- | --- | --- | --- |
| 定时同步 | 后台 goroutine | `OFFICIAL_PRICING_SYNC_INTERVAL`，默认 6 小时 | 保底：没人访问也会更新 |
| 按需刷新 | 有人访问 `/api/pricing/leaderboard` | 快照年龄 > `OFFICIAL_PRICING_STALE_SECONDS`（默认 1 小时） | 兜住「定时器还没到点但官方刚改价」 |
| 手动刷新 | 管理端按钮 | 随时 | 排障与立即生效 |

三层共用同一个 `refreshOfficialPricing()`，也就共用同一把锁——不会出现两个
刷新同时写库。

关键点：**按需刷新是异步的**。`GetPricingLeaderboard` 里只做
`maybeRefreshOfficialPricingAsync()` 就返回，用户拿到的是当前快照；刷新在
后台 goroutine 里跑完，下一次请求（或前端 5 分钟轮询）就是新的。排行榜响应
时间不受上游网速影响。

```go
// controller/official_pricing.go
func GetPricingLeaderboard(c *gin.Context) {
    snapshot, hasSnapshot := loadOfficialPricingSnapshot()
    maybeRefreshOfficialPricingAsync()   // 不阻塞，10 分钟冷却
    ...
}
```

## 2. 源失败不再让快照缩水

hc41 有个隐患：两个源里只要有一个失败，合并结果就只剩另一个源。线上
models.dev 在境内经常握手超时，所以真实情况是「偶尔某次成功拿到 3764 条，
下一次超时掉回 403 条」，价格榜的官方对比列会凭空消失一大片。

现在按源分别沿用：

```
本次 basellm 失败、models.dev 成功
  → 从上一版快照里挑出 Source == "basellm" 的条目，原样带过来
  → 快照里记 carried: ["basellm"]，排行榜底部明说「basellm 拉取失败，沿用上次数据」
```

只有**两个源都失败**时才整体报错，此时不写库，旧快照原封不动。

## 3. 条件请求：源没变就不重传

快照里按源存 `ETag` / `Last-Modified`，下次抓取带上 `If-None-Match` /
`If-Modified-Since`：

- 源返回 `304` → 不下载 body（models.dev 是 700KB gzip），直接沿用上一版条目
- `304` 也算一次成功检查，`fetched_at` 会刷新，`last_error` 会清空
- `304` 不带新 ETag 时保留旧的，下次还能继续条件请求

`304` 不会被当成失败——这点有专门的子测试（带/不带 ETag 两种）。

## 4. 内容指纹：没变就不重写

合并结果按「名字 + 源 + 三个价格（4 位小数）」算 sha256 前 8 字节，存成
`revision`。

- 内容没变 → `updated_at` 保持在「上次真正变化」的时刻，`unchanged: true`
- 内容没变且 10 分钟内刚写过 → 连库都不写，只返回结果

这样 6 小时一次的空转不会把 option 表写来写去，也给了运维一个判断依据：
`updated_at` 很久没动 = 官方价确实没改，不是同步坏了。

## 5. 三个缓存，别让公开接口替管理员买单

`/api/pricing/leaderboard` 是公开只读接口，但每次请求原来要做两件重活：

| 重活 | 量级 | 处理 |
| --- | --- | --- |
| 反序列化快照 JSON | 3803 条、约 500KB | 按 option 原始字符串缓存（命中时是 O(1) 的 string 比较） |
| 规范化匹配索引（含排序） | 3803 条排序 | 按 `revision` 缓存 |

两个缓存都在快照内容变化时自动失效，不需要额外通知。

## 6. 配置

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `OFFICIAL_PRICING_SYNC_INTERVAL` | `21600`（6 小时） | 定时同步间隔（秒）。**0 = 关闭自动同步**，退回只有手动按钮 |
| `OFFICIAL_PRICING_STALE_SECONDS` | `3600`（1 小时） | 快照多久算过期，过期时访问排行榜会触发后台补刷 |

非 master 节点不跑定时任务（`common.IsMasterNode`）。Redis 可用时刷新锁是
跨节点的（`SET NX` + 3 分钟 TTL + owner 校验释放），多副本不会一起去打上游。

## 7. 前端

### 价格榜

底部状态行从「官方价同步于 X」变成一句能自证的话：

```
官方价同步于 2026/11/21 09:30:00 (5 分钟前) · 自动同步（每 6 小时）
```

异常情况直接说出来，不藏在日志里：

- `· 正在后台更新`（快照已过期，后台正在补）
- `· models.dev 拉取失败，沿用上次数据`

`usePricingLeaderboard` 的 `staleTime` 从 5 分钟降到 30 秒，加 5 分钟轮询和
`refetchOnWindowFocus`——切回标签页就重取，不需要手动刷新页面。

### 管理端

「上游价格同步」页的工具条右侧多一行状态：

```
自动同步：每 6 小时 · 上次同步 5 分钟前
```

关闭自动同步时显示「自动同步已关闭，只能用按钮手动刷新」，避免运维以为定时任务坏了。

## 10. 已知边界

1. **「实时」的上限是上游的更新频率**。basellm 的表达式表和 models.dev 的
   成本表都不是秒级变化的数据；6 小时定时 + 1 小时过期阈值已经比它们的真实
   更新频率密得多。想更激进就调 `OFFICIAL_PRICING_SYNC_INTERVAL`，但别调到
   分钟级——models.dev 单次 30~40 秒，会持续占着上游带宽。
2. **容器内没有代理时 models.dev 基本拉不到**（境内 TLS 握手超时）。代码跟随
   `HTTP_PROXY` / `HTTPS_PROXY`，要覆盖更全就把代理配上。拿不到时快照只剩
   basellm 那 403 条，但**不会缩水**（沿用机制）。
3. **自动同步只在 master 节点跑**。多副本部署时其它节点靠 option 表的
   话题广播拿到新快照（`UpdateOption` 会 `BumpSyncTopic`）。
4. **多节点并发保护依赖 Redis**。没有 Redis 时只有本节点的 `TryLock`，
   多副本理论上会各拉一次；结果一样（幂等写），只是多花带宽。
5. **快照内容没变时 `aged_seconds` 会继续增长**，这是对的——`updated_at`
   才是「官方价上次变化」的时间，`fetched_at` 是「上次确认过」的时间。
