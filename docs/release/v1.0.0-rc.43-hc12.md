## 这一版在做什么

上游 new-api 已经是一个成熟的 API 分发网关，我们在此基础上补了四件事，把它变成**能对外运营**的平台：

1. **号池**——把多个上游 key 汇成一个渠道自动轮询，用户也能贡献自己的 key 换取额度；
2. **智能选路**——不再只按权重盲选，而是按渠道实测的成功率、首字延迟、实时并发选路，失败自动降权；
3. **内容安全与合规**——违规拦截、阶梯封禁、实名认证，把"能不能对外收钱"这件事补齐；
4. **运营后台**——风控中心、工单、代理分销、钱包、落地页。

> 说明：本版本以 `v1.0.0-rc.43` 为基线，融合了 hcnsec 系列二开能力（智能路由、自动模型、违规防护、实名认证、渠道健康、日志归档），并保留本仓库既有的号池 / 风控 / 工单 / 代理 / 钱包 / 落地页模块。

## 一、号池与贡献密钥

### 1.1 一个供应商一个号池

同一供应商的所有 key 会自动合并进**同一个渠道**，形成真正的"商汤号池 / 英伟达号池"，而不是散落成一堆同名渠道。

- 支持供应商：**商汤 SenseNova**、**英伟达 NVIDIA**
- key 合并时**按顺序去重**：已有 key 保持原序在前，新 key 按提交顺序追加
- 合并后渠道自动标记为多密钥渠道，按**轮询**方式取用；单条 key 的成功/失败状态按位置独立记录

### 1.2 两种入口

| 入口 | 谁用 | 能做什么 |
| --- | --- | --- |
| 号池管理 | 运营 | 粘贴上游 key、指定归属用户、验活后建渠道，并生成一批固定额度 token 分发 |
| 贡献密钥 | 普通用户 | 提交自己的 key，验活后并入号池，为自己开通该供应商的每日额度 |

用户侧提交时，所有影响额度与路由的字段（固定额度、无限额度、分组、接口地址）一律由平台锁定，用户只能提供"供应商 + 上游 key"，避免自助通道被用来刷额度或改路由。

### 1.3 每日额度与余额分账

号池 token 的余额分两部分，分开存储、分开展示：

- **固定额度**：运营侧一次性发放，用多少剩多少；
- **每日额度**：管理员统一配置上限，**每天 00:00（北京时间）自动重置**，上游 key 失效时重置为 0。

免费额度的回补上限锁死在当日赠送额度内，不会把付费额度误记成免费额度。

同供应商多 key **不叠加**：已有该供应商活跃号池 token 时，再次贡献只增加号池容量，不重复发额度、也不生成空 token。

### 1.4 贡献者视图

「我的号池」按供应商独立卡片展示：每日额度上限、今日剩余、下次重置时间。用户单次最多自助签发 10 个号池 token。

## 二、智能选路

### 2.1 五种负载均衡策略

同一优先级层内的渠道选择支持五种策略，可全局设定，也可**按分组覆盖**：

| 策略 | 选路依据 | 适用场景 |
| --- | --- | --- |
| `weighted-random` | 渠道权重加权随机 | 上游质量均等，保持原有行为 |
| `least-connections` | 当前活跃请求数最少 | 请求耗时差异大，防止慢渠道堆积 |
| `random` | 完全随机 | 压测、对权重无要求 |
| `round-robin` | 按候选列表稳定游标轮询 | 想让每个号严格均摊 |
| `smart` | 综合健康分（见下） | 上游质量参差，需要自动避坑 |

### 2.2 智能路由怎么打分

每个渠道算一个 0~1 的综合分，权重为 **健康度 45% + 相对速度 35% + 当前负载 20%**：

- **健康度**：近期成功率做时间衰减，样本不足时向中性值 0.5 收缩，避免新渠道被一次失败打死；
- **相对速度**：候选集内"最快渠道 = 1.0"，其余按比例折算，流式请求用首字延迟、非流式用总耗时；
- **当前负载**：`1 / (1 + k × 活跃请求数)`，实时反馈，防止单一渠道被打爆。

选路时**不是赢者通吃**：先取分数前 N 名组成第一梯队，再在梯队内按分数平方加权随机，让好渠道多吃但不会被吃满。

另有**探索率**兜底：按设定概率忽略分数全量随机，保证新渠道和无数据渠道能被采样到。

### 2.3 故障切换

- 渠道失败后进入**冷却期**，冷却期内得分降至 10%——不直接排除（可能是唯一候选），但基本选不中；
- 可调参数：梯队大小、探索率、失败冷却秒数、置信最小样本数、负载惩罚系数、延迟半衰期；
- 全部支持热更新，保存即生效，无需重启。

### 2.4 auto 智能模型

请求模型名写 `auto` 时，网关在"候选模型池 ∩ 目标分组可用模型"里按渠道健康度挑一个真实模型，并把请求改写成该模型。

- 候选池默认 13 个模型，可在后台增删；
- **计费仍按 `auto` 本身的倍率**，用户看到的价格不变，不需要理解背后换了哪个模型；
- 小概率在候选内均匀探索，让新加入池子的模型能积累健康样本。

### 2.5 会话粘性（渠道亲和）

同一会话固定走同一渠道，避免多轮对话在不同上游之间跳来跳去导致上下文不一致。

- 会话键可取自：**请求头、上下文变量、请求体字段（JSON 路径）**，支持多个来源组合；
- 规则可按**模型正则 / 路径正则 / User-Agent 包含**匹配，每条规则可独立设定 TTL、是否在失败时切换、是否把分组/模型名/规则名并入会话键；
- 支持在命中规则时**覆盖请求参数**（如固定 temperature）；
- 渠道被禁用时可选保留或立即失效。

## 三、内容安全与合规

### 3.1 违规防护（VGuard）

两级词库 + 行为窗口判定：

- **强命中**立即拦截并按阶梯封禁；**弱命中**只计数，累计到阈值才封禁——降低误伤；
- **阶梯封禁**：默认 `4, 24, 168, 720` 小时，第 N 次违规取第 N 档，屡犯递增直到永久；
- **防护提示词注入**：窗口内被标记过的用户，后续每次请求前置一段安全提示词，把用户往合规方向引导而不是直接拒绝；
- **输出侧检测**：不止看用户输入，也看模型输出；
- **LLM 二次审核**：可疑请求交给审核模型判定，支持 `chat` 与 `responses` 两种协议、同步快判 + 异步复核双段、并发上限、模型故障冷却；连续判定安全会自动缩短观察窗，审核服务不可用时按配置放行或拦截；
- **事件落库 + 动作审计**：每次命中都有记录，可追溯、可申诉；
- **邮件通知**：警告与封禁可分别配置主题与正文，带每日发送上限防轰炸。

### 3.2 实名认证

四条可用路线 + 一条预留：

| 方式 | 标识 | 说明 |
| --- | --- | --- |
| 手机短信 | `phone` | 短信验证码校验手机号归属 |
| 身份证二要素 | `id2` | 姓名 + 身份证号，对接市场 API，请求体模板与成功判定可配 |
| 分级认证 | `tiered` | 用量或累计充值达到阈值后，自动要求升级为二要素 |
| 人工审核 | `manual` | 运营侧审核材料 |
| 网证 | `national` | 预留接口，暂未启用 |

配套策略：

- 可按用户分组、白名单控制适用范围；
- 未实名可分别阻断**中继调用 / 充值 / 留言**；
- **一证一号**：同一证件不允许绑定多个账号；
- 手机号与证件号均加盐哈希存储，支持自定义 pepper；
- 可设最低年龄门槛；
- 用户侧在「个人资料」有独立实名卡片，展示当前状态与升级入口。

## 四、运营后台

### 4.1 风控中心

- **六类规则**：限流、滥用、上游 key 无效、上游 key 过期、异常用量、多账号；
- **四种作用域**：全局、按用户、按渠道、按供应商；
- **四种处置**：警告、限流、**摘除号池**、封号；
- **封禁策略**：按风险类型配置自动封禁，支持临时（按小时）与永久；
- **风险事件**：每次命中生成一条事件，可人工处置与关闭；
- **引擎**：每 10 分钟自动扫描一次（仅主节点），也可在后台手动触发一次。

### 4.2 工单

- 用户侧：提交工单（咨询 / 申诉 / 反馈 / 投诉）、会话式追问；
- 运营侧：工单列表、改状态（待处理 / 处理中 / 已解决 / 已关闭）、回复；
- 优先级四档，可按紧急程度排序处理。

### 4.3 代理分销

- 用户提交代理申请，运营侧审核通过 / 驳回；
- **两级分成**：一级比例、二级比例分别配置；
- 可设最低提现门槛；
- 公开招商页（`/affiliate`）读取同一份配置，无需另外维护文案。

### 4.4 钱包

用户一个页面看全钱的事：余额概览、充值（多种支付方式）、订阅套餐、分销收益、余额划转、账单历史。

### 4.5 落地页

首页由 Hero / 功能特性 / 使用流程 / 数据统计 / 行动号召五个板块组成，运营可在后台替换为**自定义 HTML 或外部页面地址**，嵌入时会自动同步站点的主题（明/暗）与语言。

## 五、统一配置：请求策略

所有影响"一个请求怎么被处理"的开关收敛到一个页面，分六个分区：

| 分区 | 管什么 |
| --- | --- |
| 请求检查 | 敏感词检查、检查时机（输入 / 提示词） |
| 违规防护 | VGuard 词库、处置动作、封禁阶梯、LLM 审核、邮件通知 |
| 实名认证 | 认证方式、适用范围、阻断策略、供应商参数 |
| 会话与重试 | 会话粘性规则、重试次数、可重试 / 可停用状态码、停用关键词 |
| 渠道调度 | 全局策略、按分组覆盖、智能路由六项参数、auto 模型候选池 |
| 渠道健康 | 自动探活开关、周期、并发数、探活模式、失败停用与自动恢复阈值 |

保存时**先整体校验再落库**：任何一个字段非法，整批不写入，内存状态也不会被改脏——不会出现"保存了一半"的中间态。

## 六、部署与运维

### 6.1 镜像

多阶段构建，运行层只有二进制 + CA 证书 + 时区数据，**镜像 197 MB**。

- 前端资源编译进二进制（`go:embed`），单文件启动，无静态目录依赖；
- 版本号在构建时从仓库 `VERSION` 文件注入，镜像内 `/api/status` 与界面左上角显示一致；
- 内置 `HEALTHCHECK`，30 秒探一次 `/api/status`；
- SQLite 默认开启 WAL 与 30 秒 busy_timeout，降低并发写锁冲突；
- 时区固定 `Asia/Shanghai`，日志目录挂 `/data/logs`。

### 6.2 三套编排

| 文件 | 用途 | 特点 |
| --- | --- | --- |
| `docker-compose.yml` | 本地 / 单机 | 可直接 build，数据卷 `./data` |
| `deploy/docker-compose.prod.yml` | 生产（只跑镜像） | 不 build；默认只监听 `127.0.0.1`；强制要求设置 `SESSION_SECRET`；日志轮转 20 MB × 5 |
| `deploy/docker-compose.baota.yml` | 宝塔面板 | 附带 MySQL 8.2 + Redis 7；数据库加健康检查并对齐启动顺序；不再依赖本地构建 |

`deploy/` 下另附 `.env.example`，复制成 `.env` 改三行即可用。

### 6.3 日志归档

消费日志与违规事件各自按**独立的**热保留天数轮转：

- 超过热保留天数的完整自然天，导出为 zstd 压缩的 NDJSON；
- **核对行数一致后**才从数据库删除，避免归档过程中丢数据；
- 归档文件本身再按保留天数自动清理；
- 调度器每小时触发一次，每次每张表最多推进一天，不会长时间占库。

### 6.4 自检脚本

仓库根目录 `docker-selftest.sh`，`--full` 模式覆盖 14 项：构建、冷启动、前端资源内嵌、库文件名、日志目录、健康检查、重启后数据持久化、旧库迁移不覆盖、清理。上线前跑一遍即可。

## 七、本版修复

| 问题 | 影响 | 处理 |
| --- | --- | --- |
| 号池渠道合并多 key 后未标记为多密钥渠道 | 整串 key 被当成**一条**密钥发给上游，号池请求必然鉴权失败 | 合并后按实际条数标记为多密钥，并固定轮询模式 |
| 号池 key 合并不保证顺序 | 轮询下标与单 key 状态表按位置索引，重排后坏 key 被当可用、好 key 被跳过 | 改为"已有 key 原序在前，新 key 按提交顺序追加"并去重 |
| 镜像内版本号为空 | `/api/status` 版本位空白，无法判断线上跑的是哪个版本 | 改为构建时读 `VERSION` 文件，支持 `--build-arg` 覆盖 |
| 数学公式渲染未显式关闭 `trust` | 页面被注入原型链污染时，公式里的外部引用可能被渲染并发出请求 | 显式传 `trust: false`，堵住该路径 |

### 质量验证

- 前端自动化测试 **200 个文件 / 2431 个用例全绿**；
- 镜像自检 **14/14 通过**；
- 浏览器逐页复核 11 个页面（请求策略六分区 + 号池 / 风控 / 工单 / 代理 / 使用日志），**0 个接口 4xx、0 个控制台报错**；
- 生产库 50 张表 / 5 个渠道完整迁移，容器重启数据不丢，空载内存约 31 MB。

## 八、升级指引

### 从旧版本升级

1. **备份数据库**（SQLite 直接复制 `new-api.db`；MySQL 用 `mysqldump`）；
2. 拉取新镜像并替换编排文件里的 tag；
3. `docker compose up -d`，启动时自动建表，**不需要手工执行 SQL**；
4. 打开后台确认版本号与渠道数正常。

### 需要留意的默认值变化

**默认分组的选路策略会变成"智能路由"。** 新版本的负载均衡配置默认给 `default` 分组配了 `smart`（按健康度选路），而旧版本默认是 `weighted-random`（加权随机）。

如果希望保持旧行为：**设置 → 请求策略 → 渠道调度**，把"按分组策略覆盖"里 `default` 那一行移除，或把全局策略显式设为加权随机。

### 回滚

镜像与数据库都向上兼容，回滚只需把镜像 tag 换回旧版本。由于新版本会创建新表（实名、违规事件、手机验证码等），旧版本不会读取它们，不影响运行。

## 九、下一版预告

- **渠道调度保存报错**：本版在"请求策略 → 渠道调度"页保存时会报 `not a request policy option: loadbalance_setting.*`，原因是后端保存白名单漏了该配置组的字段。修复已完成，随下一版发布。
- **签到额度进免费额度**：签到奖励不再进永久付费余额，改存用户「免费额度」，请求扣费时优先消耗免费额度、不污染付费余额（与号池 token 的免费/付费分账逻辑对齐）。个人页新增「免费额度」指标，签到成功提示与说明同步点明。免费额度**累计不清零**（不做每日重置）。代码已完成并通过单测，随下一版发布。
- 号池清理工具：一键识别并合并重复的号池渠道、清理失效 key。
- 一键部署脚本：`deploy.sh` 完成备份 → 拉镜像 → 迁移 → 健康检查 → 回滚点标记。

> 已知限制：与号池 token 的现有实现一致，在开启批量更新（`BATCH_UPDATE_ENABLED=true`）的部署下，`free_quota` 覆盖层在批量落库路径不单独更新，仅影响「免费/付费」的展示拆分精度，实际可用余额与扣费顺序不受影响。
