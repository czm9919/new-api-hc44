# v1.0.0-rc.43-hc19 发版说明

## 主题:巡检覆盖上游全量模型(自动发现新模型)

hc18 的单模型巡检只检测「渠道已配置」的模型,上游新增的模型永远不会被发现。hc19 让号池渠道在每轮巡检前先向上游拉取全量模型列表,以**上游实际提供的模型**为检测范围。

## 功能变更

### 1. 号池渠道巡检前自动刷新上游模型列表
- 逐模型巡检(`ModelAutoCheckEnabled`)开始时,对号池渠道(tag 前缀 `keypool-`)用渠道内的有效 key 调上游 `GET /v1/models` 拉取全量模型列表,再按刷新后的列表逐个检测;
- **上游新增的模型自动绑定**:写入渠道 `models` 与 `abilities`,默认上架,并立即参与本轮检测;
- **上游已下线的模型自动移除**:`abilities` 行删除,不再参与调度;
- **既有模型不受刷新影响**:被自动下架的坏模型不会被刷新重置上下架状态;
- 拉取失败(所有 key 均无效/上游不可达)时保持现状,只检测已配置的模型;
- 后台「自动绑定上游模型」(`keypool_auto_bind_models`)关闭时跳过刷新——模型列表由运营手动管理。

### 2. 巡检摘要新增 `models_added` 计数
系统任务历史中的巡检结果新增「本次新发现并绑定的模型数」。

### 3. 修复:内存缓存模式下单模型下架不生效(hc18 缺陷)
`MEMORY_CACHE_ENABLED=true` 时,调度缓存按渠道 `models` 全量构建,不感知 abilities 的 `enabled=false`,导致单模型下架要等下一次缓存同步(且同步后仍会失效)。hc19 在缓存构建时显式排除被下架的 (channel, model) 组合,并在下架/上架、模型列表刷新后即时刷新缓存。

### 4. 修复:巡检结果汇总丢失逐模型计数(hc18 缺陷)
`runChannelTestWorkers` 的结果归并没有累加 `models_delisted`/`models_recovered`,多渠道巡检的总摘要里这两个计数恒为 0。已修复。

## 升级步骤

```bash
# 1. 替换镜像 tag(hc19)
#    deploy/docker-compose.prod.yml / baota.yml 已更新为 delta-api/new-api:v1.0.0-rc.43-hc19
# 2. 导入镜像并重启
docker load < new-api-v1.0.0-rc.43-hc19.tar.gz
docker compose -f deploy/docker-compose.prod.yml up -d
```

无需数据库迁移;无新增配置项(行为跟随既有的 `monitor_setting.model_auto_check_enabled` 与 `keypool_auto_bind_models`)。

## 注意事项
- 号池渠道每轮巡检会多 1 次 `GET /v1/models` 请求(每渠道 1 次,非每模型);
- 非号池渠道行为不变(仅检测渠道已配置的模型);
- 已知环境性存量失败(与本次改动无关):`controller` 包 `TestAuditDatabaseMatrix`/`TestAdminUserRiskOperations*`(Windows TempDir 文件占用)、`service` 包 channel affinity 2 例。
