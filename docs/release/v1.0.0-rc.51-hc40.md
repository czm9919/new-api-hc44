# v1.0.0-rc.51 · hc40：签到不再像「付费额度 + 免费额度发两次」

**主题**：统一签到入账语义与个人页余额口径 —— 签到只送免费额度，付费余额一分不动。

## 现象

开启签到后签一次到，个人页顶部两张卡同时变大：

- 「当前余额」+奖励
- 「免费额度」+奖励

看起来像同一笔奖励发了两遍，或者「付费额度」也被塞了一次。钱包页显示的却是另一套数字
（付费余额不变、免费额度 +奖励），两边对不上。

## 根因：两个字段的关系被展示层弄丢了

`user.quota` 是**工作余额总额**，`user.free_quota` 只是其中标了「免费」的那部分：

```
付费余额 = quota - free_quota
总可用   = quota
```

签到发奖必须**同时**抬 `quota` 与 `free_quota`：

- 只加 `free_quota` → 破坏 `free_quota <= quota` 不变量，付费余额变负、扣费时重复扣减；
- 只加 `quota` → 奖励变成永久付费余额，与「签到送免费额度」的产品口径相反（hc12 定的）。

所以后端行为从 hc12 起就是对的。错的是**个人页把 `quota` 直接当「当前余额」展示**：
它包含免费额度，于是签到后「当前余额」跟着涨，而紧挨着的「免费额度」也涨 —— 两张卡都动，
自然像重复发奖。钱包页（hc20）和用户管理列表（hc23）早就是 `quota - free_quota` 的付费余额口径，
只有个人页这一处漏了。

## 改动

### 前端：个人页按钱包口径拆开

`web/src/features/profile/components/profile-header.tsx`

| 卡片 | 改前 | 改后 |
| --- | --- | --- |
| 第 1 张 | 当前余额 = `quota`（含免费） | **付费余额 = `quota - free_quota`**，副标题写「可用余额 `<quota>`」 |
| 第 4 张 | 免费额度 = `free_quota` | 不变 |

签到后只有「免费额度」和副标题里的总可用变化，付费余额卡纹丝不动，与钱包页、用户管理列表完全一致。

拆分逻辑抽到 `web/src/features/profile/lib/format.ts: splitProfileQuota()`：
总额为正时付费余额钳到 0（脏数据不让它显示负数），透支（总额为负）时保留负号。

### 后端：两条入库路径合一，补上钱包上限守卫

`model/checkin.go` 原本有两条入账 SQL：

- MySQL / PostgreSQL 的事务路径：自己写 `Updates(map{quota: +N, free_quota: +N})`
- SQLite 的直写路径：调 `IncreaseUserFreeQuota()`

两条语义相同但实现分叉，事务路径还漏了 `MaxWalletQuota` 守卫（极端情况下能把余额推过上限）。
现在抽出 `model/user.go: increaseUserFreeQuotaTx(db, id, quota)`，两条路径共用同一段 SQL：

- `quota` 与 `free_quota` 同步 +奖励
- `quota <= MaxWalletQuota - 奖励` 守卫，超限整笔失败（事务路径回滚签到记录，SQLite 路径删除记录）
- 付费余额 `quota - free_quota` 在签到前后严格不变

### 脚本的三个动作（重要）

```
docker stop new-api
python verify-hc40.py prepare     # 容器停着时插临时用户
docker start new-api
python verify-hc40.py             # 只走 HTTP
docker stop new-api
python verify-hc40.py cleanup     # 容器停着时删临时用户
docker start new-api
```

**不要边跑边写库**：SQLite 走 WAL，容器在写的同时外部进程再写会把 freelist 写花，
之后 `SELECT ... ORDER BY id` 直接 `SQLITE_CORRUPT(11) database disk image is malformed`
（本轮第一次尝试就踩到了）。prepare / cleanup 必须在容器停止后执行，脚本会先打
`integrity_check` 再动手。

## 离线包

两种格式，同一镜像，任选其一：

| 文件 | 大小 | sha256 |
| --- | --- | --- |
| `new-api-v1.0.0-rc.51-hc40.tar` | 41,785,856 | `ff2a8720bcf98672d47bb70ce599e7ecf47cbc20d6d79f9bf5d89f8e7e0fd435` |
| `new-api-v1.0.0-rc.51-hc40.tar.gz` | 41,226,452 | `aff0592b52da6fe056a44062ed96ce3387f9594b7317a3476f1ed79def588de9` |

```bash
docker load -i new-api-v1.0.0-rc.51-hc40.tar      # 直接可用
docker load -i new-api-v1.0.0-rc.51-hc40.tar.gz   # gzip 由 docker 自动解
```

`.tar` 版实测 `docker load` 回 `Loaded image: delta-api/new-api:v1.0.0-rc.51-hc40`，
image ID `97edbc13f568`，165MB；manifest 里的 RepoTag 与我方镜像名一致，可直接再
`tag` 或直接跑。两者大小几乎相同，因为镜像内的 `new-api` 二进制本身已是压缩过的
Go 产物，gzip 只多压掉 559KB。

> 格式说明：本机是 Docker **29.9.2 + containerd 镜像存储（overlayfs）**，所以
> `docker save` 出的是 **OCI 布局**（`blobs/sha256/*` + `manifest.json`，16 个条目），
> 不是老式 graph driver 的 `<hash>/layer.tar` 平铺结构。`.tar` 与 `.tar.gz` 的布局完全
> 相同，只是后者多包了一层 gzip，**兼容性上没有任何区别**。老主机若 `docker load`
> 报 `unrecognized image format`，找一台新 Docker `load` 后重存一次即可。
